# 基于 Spring Boot 的 AI 培训计划管理系统
## 开题准备总结：技术栈 / 功能 / 痛点 / 进度

> 题目已由导师确认，功能方向已定稿（见第三部分），技术栈沿用导师认可的前后端方案。
> 本文件用于开题报告撰写，可直接取用其中的表述。

## 一、题目与系统定位

- **论文题目**：基于 Spring Boot 的 AI 培训计划管理系统设计与实现
- **系统定位**：面向企业/组织内部培训的业务管理系统，以「岗位技能差距」为数据主线，
  在「培训方案生成」与「培训效果诊断」两个环节引入大语言模型做智能增强。
- **一句话概括**：把"凭经验拍脑袋的集体培训"变成"基于技能差距的个性化培训闭环"。

论文落点：六个功能模块与「需求分析 → 系统设计 → 系统实现 → 系统测试」四章一一对应，
AI 相关部分单独成节，并配一组对比实验支撑论文的实验章节。

## 二、技术栈（精简优先版）

**选型原则：单人、单机、一个学期。能用现成模板和代码生成器解决的，绝不手写；
中间件只要不是非用不可，就不引入。** 功能范围是导师定的，不能砍；
技术复杂度没有硬性要求，可以砍——省下来的时间投到 AI 模块和论文上。

| 层次 | 选型 | 必要性 | 用途说明 |
| --- | --- | --- | --- |
| 前端框架 | Vue 3 + Vite | 必选 | 管理端页面（管理员/主管/员工三类角色） |
| 前端 UI | Element Plus | 必选 | 表单、表格、弹窗、菜单，覆盖 90% 页面需求 |
| 前端路由 | Vue Router + Axios | 必选 | 页面跳转与接口请求封装 |
| 前端可视化 | ECharts | 强烈建议 | 技能差距雷达图、进度看板、前后对比图；代码量极小但论文配图价值高 |
| 前端状态 | Pinia | 可选 | 小项目可只用 localStorage 存登录信息与用户角色 |
| 后端框架 | Spring Boot 3.x（Java 17）+ Spring MVC | 必选 | 业务接口 |
| 持久层 | MyBatis-Plus | 必选 | 自带代码生成器，六张表的增删改查可自动生成 |
| 认证授权 | Sa-Token + JWT（或简化配置的 Spring Security） | 必选 | 登录、角色权限。Sa-Token 几行注解就能做角色校验，比 Spring Security 上手脚快得多 |
| 接口文档 | Knife4j / Swagger | 强烈建议 | 几乎零成本，接口文档截图可直接用于论文 |
| 数据库 | MySQL 8 | 必选 | 业务数据：用户、岗位、技能、计划、进度、题库、成绩 |
| 工具库 | Lombok、Hutool | 必选 | 少写大量样板代码 |
| 构建与测试 | Maven、Git、Postman | 必选 | 依赖管理、版本控制、接口测试 |
| 性能测试 | JMeter | 可选 | 只需对登录/查询接口做一次并发测试，产出论文测试章节的响应时间表 |
| 缓存 | Redis | 可省 | 单机小规模项目无必要，JWT 本身无状态 |
| 容器与部署 | Docker | 可省 | 演示时本地起 MySQL + 启动后端 + `npm run dev` 即可 |
| 绘图 | draw.io / ProcessOn | 必选 | 架构图、E-R 图、流程图、用例图 |

**降低难度的三个关键手段（效果远比砍技术栈明显）**

1. **MyBatis-Plus 代码生成器**：把六张核心表设计好之后，直接用生成器产出 Entity、
   Mapper、Service、Controller 和前端基础页面，半天就能把六套 CRUD 骨架搭完，
   你的时间应该花在技能差距算法和 AI 模块上。
2. **现成的 Vue3 + Element Plus 后台管理模板**：登录页、侧边菜单、布局、用户管理、
   表格分页这些通用部分直接复用，改配色和字段即可。这类模板网上很多，挑 Vue3 版本的
   （不要用 Vue2 的旧模板）。
3. **大模型调用自己封装一个 Service**：用 RestTemplate/OkHttp 发 HTTP 请求，
   Prompt 存配置文件或数据库。不建议一上手就用 Spring AI 或 LangChain4j 这类框架，
   版本兼容问题会让你把时间浪费在排查环境上，而这部分对你的论文没有任何加分。

以后若被问到"为什么不用 Redis / 微服务 / 中间件"，
标准回答：项目为单机部署、单人开发、数据规模小，选型以开发效率与可维护性优先，
架构上预留扩展位（如缓存层、接口层）。这段话也可以直接写进论文的技术选型小节。

## 二之二、AI 模块技术方案（RAG + 工作流编排）

RAG 是共识，值得加；工作流编排用不用 LangGraph，二选一。
**注意：导师此前说明"技术栈按提交的那些来"，追加 AI 侧技术栈前先与导师确认。**

**为什么建议加 RAG**

- 面试/答辩层面的价值：把"调用大模型"变成"检索增强生成"，
  有检索召回、引用来源、可对比实验（有 RAG / 无 RAG），直接构成论文实验章节。
- 与业务自然结合的场景：
  - 培训方案生成时，先检索岗位技能标准、课程大纲、培训制度，再生成方案说明（带依据引用）；
  - 员工侧"技能标准问答 / 课程内容问答"；
  - 考核模块生成题目时检索知识点范围。

**RAG 的两个前置条件（必须先解决，否则是空壳）**

1. **语料库**：需要真实可检索的文档。可选来源——国家职业技能标准（人社部公开发布）、
   公开课程标准与教学大纲、自建的培训制度与课程说明文档、岗位说明书。
   建议整理成 50–200 篇文档、切分成几百到上千个知识片段。
2. **向量化与检索**：知识片段规模在千级以内时，用内存向量 + 余弦相似度即可，
   不必引入 Milvus、Elasticsearch 这类重型向量库（论文中可表述为"轻量级向量检索，
   降低部署复杂度"）。嵌入模型用国产 API（如通义 text-embedding、智谱 embedding-3），
   避免本地模型下载与显存问题。

**工作流编排的两种实现路径**

| 方案 | 做法 | 代价 | 适合 |
| --- | --- | --- | --- |
| A：LangGraph | 单独起 FastAPI + LangGraph 服务，把方案生成建模为状态图（拉取差距数据 → 检索知识库 → 生成 → 结构化校验 → 失败回退 → 人工确认 → 写回） | 多一套 Python 服务，双语言联调、两套环境、两处部署；LangGraph 版本迭代快，遇到问题资料相对少 | Python 基础过关、且 11 月中旬前能跑通一条完整链路 |
| B：自研轻量编排 | 全部在 Spring Boot 内实现，用 Service 编排顺序 + 状态字段 + 重试，RAG 检索在 Java 侧调用向量检索接口 | 答辩时"技术名词"没有 A 亮眼，但功能与实验完全不受影响 | 时间紧、只想稳稳做完的人（推荐） |

**如果选 A，架构是**：Vue 前端 → Spring Boot（业务与权限）→ HTTP → Python AI 服务
（FastAPI + LangGraph + RAG）→ 大模型与向量检索。
边界清晰、职责分明，论文里作为"AI 服务独立部署"来写是加分项；
但工程量会从"一个系统"变成"两个服务"，这是必须提前想清楚的代价。

**无论选哪种，实验对比都要设计好（论文实验章节的骨架）**

| 对比项 | 目的 |
| --- | --- |
| 无 RAG vs 有 RAG | 证明检索增强在方案合理性与依据充分性上的提升 |
| 单次调用 vs 工作流（含校验重试） | 证明结构化校验与重试机制提升输出合规率 |
| 规则方案 vs 纯 LLM vs 混合策略 | 论文核心对比实验，支撑"混合策略"这一创新点 |

评价指标建议：输出格式合规率、方案采纳率、专家/人工评分（3–5 人打分取均值）、
平均生成耗时、技能提升幅度（前后测差值）。

## 二之三、AI 功能清单（"必须有 AI 功能"的落点）

原则：**AI 不能只挂在一个模块上**。六个业务模块中至少有三个嵌入 AI 能力，
这样系统才是"AI 培训管理系统"，而不是"带了一个 AI 按钮的管理系统"。
每个 AI 功能都要凑齐"五件套"：数据来源 → 方法 → 输出 → 评价指标 → 对比实验，
否则答辩时被问"你的 AI 在哪"会答不上来。

| 所属模块 | AI 功能 | 输入 | 输出与作用 | 评价指标 | 必要性 |
| --- | --- | --- | --- | --- | --- |
| ② 技能差距分析 | 技能差距量化与优先级排序 | 岗位目标等级、员工当前等级、技能权重 | 差距表、培训优先级排序 | 排序结果与主管判断的一致率 | 必须 |
| ② 技能差距分析 | 员工技能画像聚类（KMeans） | 员工 × 技能等级矩阵 | 识别短板群体，支撑群体化培训计划 | 轮廓系数、群体划分合理性 | 选做（数据造好后实现成本极低） |
| ④ 方案生成 | RAG 检索增强的个性化方案生成 | 差距表 + 岗位技能标准/课程库 | 个性化学习路径 + 生成依据引用 | 格式合规率、方案采纳率、有/无 RAG 对比、人工评分 | **必须（核心）** |
| ④ / 员工端 | 技能标准与课程知识问答 | 用户提问 + 知识库 | 带引用来源的答案 | 检索命中率 Top-k、答案准确率抽检、响应时间 | 必须（演示效果最好） |
| ⑤ 进度跟踪 | 培训拖期风险预测 | 历史进度、岗位、课程时长 | 风险等级与预警提示 | 准确率、召回率、混淆矩阵 | 选做（实验章节很好写） |
| ⑥ 考核评测 | 智能组卷与主观题辅助评分 | 知识点、难度分布、答题文本 | 试卷、评分与评语 | 与人工评分的一致性（相关系数 / 加权 Kappa） | 选做（推荐做一致性实验） |
| ⑥ 考核评测 | 效果诊断与补训方案生成 | 前后测成绩、技能差距变化 | 效果诊断结论 + 补训方案 | 结论与主管判断的一致率 | 必须 |

**"真 AI" 与 "伪 AI" 的分界线（自查用）**

| 伪 AI（答辩容易被问穿） | 真 AI |
| --- | --- |
| Prompt 写死在代码里，调一次接口就返回 | Prompt 模板化管理，输入由业务数据（差距表、知识库）动态构造 |
| 没有检索，模型自由发挥，可能编造课程 | 先检索岗位技能标准与课程库，输出带依据引用 |
| 输出不校验，格式错了就报错或不管 | 强制 JSON 结构化输出 + 字段校验 + 失败重试 + 降级为规则方案 |
| 没有指标，只有一个截图 | 有合规率、采纳率、准确率等量化指标与对比实验 |
| 换个输入结果都差不多 | 输入变化能体现在输出差异上（可抽查验证） |

**AI 部分（本项目的技术核心）**

| 环节 | 做法 |
| --- | --- |
| 技能差距量化 | 技能点权重 × 目标等级与当前等级差值 → 加权归一化，输出差距排序表 |
| 方案生成策略 | **混合策略**：规则排序召回候选课程/内容 → 大语言模型生成方案说明与学习路径 |
| 大模型接入 | 国产 API（通义千问 / DeepSeek / 智谱 GLM，OpenAI 兼容接口），Prompt 模板管理 |
| 输出的可控性 | 要求 JSON 结构化输出 + 后端字段校验 + 失败重试 + 降级为纯规则方案 |
| 成本控制 | 结果缓存、限流、按需触发（仅在差距表变化时重新生成） |
| 可选增强 | 向量检索 / 知识库问答（岗位技能标准、课程内容问答）——用于补充工作量 |

## 三、功能模块（六个）

**1. 用户与角色权限管理**

- 管理员 / 主管（培训负责人）/ 员工三类角色
- 用户账号、部门、岗位信息维护
- 基于角色的菜单与接口权限控制

**2. 岗位技能模型与技能差距分析**

- 岗位技能模型：技能点清单 + 目标等级（如 1–5 级）
- 员工技能档案：本人当前等级（自评/主管确认）
- 差距量化：逐项计算差距 → 生成差距表与雷达图
- 输出：技能差距清单，按差距 × 权重排出培训优先级

**3. 培训需求与培训计划管理**

- 培训需求登记与汇总（部门/岗位维度）
- 培训计划制定：课程、时间、对象、负责人、目标技能点
- 计划审批与发布、状态流转（草稿/待审/已发布/进行中/已结束）

**4. AI 个性化培训方案生成**

- 输入：以技能差距数据为依据
- 过程：规则排序（差距大小 × 技能权重）+ 大语言模型生成方案说明
- 输出：个性化学习路径、课程顺序、学时建议、生成依据说明（可解释）
- 支持人工调整与采纳，记录采纳情况

**5. 培训实施与进度跟踪**

- 员工进度上报（学习进度、完成状态）
- 主管查看完成率、拖期预警
- 统计看板：按部门/岗位/计划统计完成率

**6. 考核与效果评测**

- 题库管理与组卷，测验自动评分（客观题自动判分，主观题可接大模型辅助评分）
- 培训前后技能/成绩对比 → 效果诊断结论
- 未达标项自动生成补训方案

## 四、痛点 → 功能 → 技术 对应关系

| 行业痛点 | 系统功能对应 | 关键技术 |
| --- | --- | --- |
| 培训"一刀切"：全员同一套课程，与岗位要求和个人现有水平脱节，学完用不上 | 岗位技能模型 + 技能差距分析 + 个性化方案生成 | 差距量化算法（加权+归一化）、规则排序、大模型生成 |
| 计划制定靠人工经验：需求靠表格收集，编排耗时，缺乏数据依据，难以规模化 | 培训需求与计划管理、AI 方案生成 | 工作流状态管理、Prompt 模板、结构化输出 |
| 过程不可视：进度靠口头或表格上报，管理者无法实时掌握，拖期难发现 | 进度上报与跟踪、完成率统计看板 | Redis 缓存、ECharts 可视化、定时提醒 |
| 效果不可量化、没有闭环：培训结束即终止，无法判断是否达标，补训靠拍脑袋 | 题库测验自动评分 + 培训前后差距对比 + 效果诊断 + 补训方案 | 自动判分、前后测对比分析、大模型生成补训建议 |

**核心痛点一句话版（开题报告摘要可用）**：
企业培训普遍存在"统一课程与岗位需求错位、计划制定依赖经验、过程进度不可视、培训效果无法量化且缺乏闭环"
四类问题，本系统以技能差距量化为数据基础，结合大语言模型生成个性化培训方案与效果诊断建议，
构建"差距诊断 → 方案生成 → 执行跟踪 → 考核评价 → 补训"的完整闭环。

## 五、创新点与工作量表述（答辩必备）

**创新点可以这样写（三条，避免被问"是不是只是调了个大模型接口"）**

1. 应用创新：将大语言模型引入培训方案生成环节，把"规则匹配出的课程清单"升级为
   "有数据依据、带解释说明的个性化学习路径"。
2. 方法融合：提出技能差距量化模型（技能权重 × 等级差距）与 LLM 生成相结合的混合策略，
   由量化结果约束生成方向，而非单纯依赖模型自由发挥。
3. 工程完整：形成培训管理从差距诊断到补训的闭环，而非单点功能。

**导师提示"工作量不够可加模块"，可加入的候选（选 1–2 个即可）**

- 移动端 / 小程序端（员工随时随地进度上报与学习）
- 培训资源与课程库管理 + 文件上传（MinIO / OSS）
- 消息通知（站内信、邮件、企业微信机器人推送）
- 管理驾驶舱数据大屏
- 智能组卷 + 主观题大模型辅助评分
- 岗位技能标准知识库 + 向量检索问答
- 权限细化到按钮级 / 数据级

**工作量不足时的正确补法**：不是加 CRUD 页面，而是增加"可量化、可对比"的内容——
模型/策略对比实验、指标统计、性能压测数据，这些直接构成论文的实验章节。

## 七、主要风险与应对
