## 三、安全问题（4 处）

### 3.1 用户列表未授权（已修）

- **现象**：以普通员工令牌请求 `GET /api/system/user/page`，返回 `code=0`、`total=64`，每条记录含手机号、邮箱、角色列表。
- **根因**：`UserController` 的写操作在 `UserService` 内部都调用了 `requireAdmin()`，唯独分页查询 `page()` 与详情 `detail()` 两个只读方法漏了校验。这是"重写轻读"的典型遗漏——写接口守得很严，读接口以为天然安全。
- **影响面**：任何已登录员工均可批量导出全员通讯信息。
- **修复**：`UserService.page()` 增加 `LoginHelper.requireManager()`，仅管理员与讲师可查。
- **验证**：员工令牌返回 `code=403 该操作仅管理员或讲师可用`；管理员令牌返回 `code=0`，未误伤正常功能。

### 3.2 用户详情水平越权（已修）

- **现象**：员工用 `GET /api/system/user/3` 可读到非本人的姓名、部门、手机号、邮箱。
- **根因**：同 3.1，`detail()` 直接按 id 查询，未校验调用者与目标的关系。
- **修复**：改为 `LoginHelper.requireSelfOrManager(id)`——本人可查自己，查他人需管理员或讲师。
- **兼容性确认**：前端仅管理端用户页调用该接口，员工端个人中心走 `/auth/me`，因此不影响现有页面。

### 3.3 登录爆破与用户名枚举（已修）

- **现象**：连续 8 次提交错误口令，均正常返回"密码错误"，无锁定、无延迟；且"账号不存在"与"密码错误"提示不同，可据此判断哪些用户名真实存在。
- **修复**：
  1. 新增 `LoginAttemptService`，按账号维度计数，连续 5 次失败锁定 10 分钟，返回 `code=429`；
  2. 两类失败统一为"账号或密码错误"，消除枚举依据；
  3. 补充 4 个单元测试覆盖计数、锁定、过期解锁、成功登录清零。
- **设计取舍**：计数键只取用户名、不叠加来源 IP。原因是校园网出口 IP 相同，按 IP 限流会误伤同网段其他用户。当前为单机内存实现，若将来多实例部署需改为 Redis 共享计数。

### 3.4 异常信息外泄（已修）

- **现象**：触发未支持的方法时返回 `系统繁忙：Request method 'GET' is not supported`，直接暴露框架行为与内部路径。
- **修复**：对外统一返回 `系统繁忙，请稍后重试（错误码 xxxxxxxx）`，完整堆栈按该错误码写入服务端日志。既不影响定位，也不泄露内部结构。

### 3.5 复测记录

```
1. 员工拉用户列表        -> code=403 该操作仅管理员或讲师可用
2. 员工查他人详情        -> code=403 只能查看或操作自己的数据
3. 员工查自己详情        -> code=0 success
4. 管理员拉用户列表      -> code=0 success
5. 触发异常              -> code=500 系统繁忙，请稍后重试（错误码 dab5102f）
6. 连续错误登录第 6 次   -> code=429 密码错误次数过多，请 10 分钟后再试
```

单元测试 49 个全部通过（原有 45 个 + 新增 4 个限流用例），无回归。

## 四、界面问题（1 处）

### 4.1 AI 指标页结论与数据相反

- **现象**：`/ai/metrics` 页底部原写"纯大模型组的平均幻觉课程数就是约束必要性的量化证据"，但同一页面表格给出的数据是：

| 生成模式 | 平均幻觉课程数 |
|---|---|
| 纯规则 | 0 |
| 规则 + 大模型混合 | 0.98 |
| 纯大模型 | 0.07 |

纯大模型的数值低于混合模式，原结论与页面数据自相矛盾。

- **根因**：两组数字统计口径不同，不可直接比较。
  - 混合组走 `validate(root, ruleCourses)` 严格校验，课程一旦超出候选集即整份方案失败降级，成功路径下 `hallucinationCount` 恒为 0；
  - 纯大模型组走 `validateLenient(root, catalog)` 宽松校验，按"课程是否存在于课程库"逐条统计。
- **修复**：将该页结论文案改为口径说明，并明确表述"约束的价值在于保证课程可选、学时可控，而非降低幻觉数"。修复后页面结论与数据一致。

该问题也修正了论文中一处表述口径：混合模式的贡献应表述为**保障预算与可执行性**，不宜表述为"防止幻觉"。

## 五、稳定性问题（1 处）

### 5.1 演示环境启动失败无降级路径

原开发用启动脚本 `start-all.bat` 在答辩场景下有 5 个确定会出问题的地方：

| 场景 | 原脚本表现 | 处理方式 |
|---|---|---|
| 3306 被本机另一套 MySQL 服务占用 | 直接退出，后端随后报 `Unknown database` | 自动探测 3306 是否为本项目库，否则改用 3307 启动独立实例，不触碰系统服务 |
| 前端用 `npm run dev` 启动 | 本机环境下开发服务器会因清理临时目录失败而崩溃 | 改为预构建产物 + `vite preview` |
| 后端与前端同时启动，不等就绪 | 前端先起来，首屏请求全部失败 | 按 数据库 → 后端 → 前端 顺序，每级做 HTTP 探测后再进入下一步 |
| `java -jar` 工作目录不对 | 读不到本地配置，数据库口令为空 | 显式切换到 server 目录再启动 |
| 上次进程残留 | 可能连到旧实例却看不出来 | 启动前清理 8000 / 3000 端口上的旧进程 |

**新增脚本**：`work/app/start-demo.bat`、`stop-demo.bat`。双击即用，失败时窗口保持不关闭，并写入 `logs/start-demo-trace.log` 记录实际使用的数据库端口、启动命令、进程号与等待轮次。

**实测结果**：

| 场景 | 数据库就绪 | 后端就绪 | 前端就绪 | 结果 |
|---|---|---|---|---|
| 冷启动（模拟答辩当天开机） | 10.0 秒 | 18.1 秒 | 21.1 秒 | 登录成功，用户表 64 条 |
| 热启动（产物已存在） | 已就绪 | 12.1 秒 | 12.1 秒 | 登录成功，用户表 64 条 |
| 首次启动（需构建前端） | 已就绪 | 8.2 秒 | 47.3 秒 | 登录成功，用户表 64 条 |

冷启动一行为停止全部服务后重新启动的结果，等同答辩当天的真实状态。

## 六、功能巡检结果

以管理员与员工两个角色，用浏览器自动化真实点击，逐页截图并收集控制台错误与失败请求。

**管理员视角：22 个页面全部正常渲染**，无白屏、无报错弹窗、无图表空框，数据均来自数据库真实记录，非占位内容。

**员工视角：12 个菜单项正确收窄**，用户管理、组织架构、技能点管理、岗位模型、进度看板、题库、试卷、知识库、效果诊断、AI 指标等管理页均不可见；直接输入 `/system/user` 会被路由守卫弹回工作台。

**端到端闭环可跑通**：员工发起技能差距分析 → 选择"纯规则"模式生成方案 → 45ms 返回 2 门课程共 10 学时，并附安排依据 → 可采纳 / 修改后采纳 / 转为培训计划。

当前数据规模：64 名用户、30 门课程、7 个培训计划、80 道题目、2 份试卷。

## 七、已知限制与取舍

以下三项经评估后**未做改动**，理由如下：

| 项 | 现状 | 理由 |
|---|---|---|
| 接口文档未做认证 | `/doc.html`、`/v3/api-docs` 可匿名访问 | 系统定位为校内教学演示，答辩需现场展示接口文档；且仅暴露接口签名，不含业务数据。若转为正式上线，应关闭或加登录校验 |
| 令牌存于 localStorage | 前端 `stores/user.ts` | 改为 HttpOnly Cookie 需重建跨域与 CSRF 方案，工程量与收益不匹配；当前无 `v-html`，XSS 面很小 |
| 无员工自助改密 | 重置密码仅管理员可用 | 属功能欠缺而非安全缺陷，本期不扩展 |
