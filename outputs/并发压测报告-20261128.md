# 并发压测报告

**系统**：AI 培训计划管理系统
**时间**：2026-11-28
**目的**：为「系统测试」章节提供可复现的性能证据，并核实需求清单第 13 项「接口响应 ≤ 2 秒」

---

## 一、测试环境与方法

### 1.1 环境

| 项 | 配置 |
|---|---|
| 机器 | 单机 Windows 11，12 逻辑核心，16 GB 内存（测试时可用约 2 GB） |
| 后端 | Spring Boot 3.3.5 / Java 21，Tomcat 默认 200 工作线程 |
| 连接池 | HikariCP，`maximum-pool-size: 10` |
| 数据库 | MySQL 8.0.45 独立实例，`127.0.0.1:3307`，与本机 MySQL80 服务隔离 |
| 客户端 | Python 3 `http.client`，多线程，长连接（keep-alive），单进程 |
| 数据规模 | 64 用户 / 30 课程 / 80 题 / 7 培训计划 / 20 技能 / 197 条学习进度 |

### 1.2 方法

1. **成功判定按响应体而非 HTTP 状态码**。本系统统一返回 `HTTP 200`，业务结果在响应体 `code` 字段（`{"code":0,...}` 为成功）。若只统计 HTTP 状态，会把业务失败也算成成功——第一版脚本正是这样误判的，已废弃。
2. **每个场景重复 3 轮取中位数**。本机内存压力较大（浏览器与工具占用 14 GB），单次采样波动可达 3 倍，单轮数据不可用。
3. **压测接口不含任何大模型调用**，全部为数据库读或本地计算，排除网络与模型延迟干扰。
4. 每轮先预热 5–10 次，排除 JVM 即时编译与连接建立的首次成本。

## 二、串行基线（单请求延迟）

每接口连续 30 次串行请求，全部成功（`code=0`）。

| 接口 | 中位延迟 | P95 | 最大 |
|---|---:|---:|---:|
| 技能列表 `/skill/list` | 1.0 ms | 1.4 ms | 2.3 ms |
| 课程分页 `/train/course/page` | 2.1 ms | 2.5 ms | 3.3 ms |
| 题库分页 `/exam/question/page` | 2.5 ms | 3.6 ms | 3.8 ms |
| 需求分页 `/train/need/page` | 2.9 ms | 5.5 ms | 25.3 ms |
| 用户分页 `/system/user/page` | 3.1 ms | 5.4 ms | 26.4 ms |
| 计划详情 `/train/plan/2` | 3.1 ms | 5.0 ms | 18.9 ms |
| 技能热力图 `/skill/gap/heatmap` | 4.6 ms | 6.8 ms | 7.0 ms |
| 计划分页 `/train/plan/page` | 8.3 ms | 10.8 ms | 11.0 ms |

**最慢的业务接口 P95 为 10.8 ms，距 2000 ms 的要求有两个数量级余量。**

## 三、并发吞吐

7 个轻量读接口混合请求（不含热力图），每轮 12 秒，重复 3 轮取中位数。

| 并发数 | 吞吐 | 中位延迟 | P95 | P99 | 成功率 | 三轮吞吐 |
|---|---:|---:|---:|---:|---:|---|
| 10 | **1309 req/s** | 6.4 ms | 19.2 ms | 22.0 ms | 100 % | 1092 / 1309 / 1349 |
| 30 | **1464 req/s** | 11.5 ms | 68.7 ms | 185.8 ms | 100 % | 1478 / 1464 / 1375 |

并发从 10 提到 30，吞吐只涨 12%，说明瓶颈已不在应用层：Hikari 连接池上限 10，30 并发时存在排队，延迟随之上升但仍在 70 ms 量级。

## 四、瞬时突发

模拟答辩现场「多人同时点开同一个页面」：N 个线程在同一时刻发出同一请求（`/train/plan/page`），各重复 3 轮取中位数。

| 同时请求数 | 全部成功 | 墙钟耗时 | 平均 | P95 | 最大 |
|---:|---:|---:|---:|---:|---:|
| 50 | 50 / 50 | 0.11 s | 58.0 ms | 98.9 ms | 100.6 ms |
| 100 | 100 / 100 | 0.23 s | 116.5 ms | 204.8 ms | 215.9 ms |
| 200 | 200 / 200 | 0.51 s | 238.5 ms | 437.4 ms | 476.0 ms |

200 个并发在同一瞬间打到同一接口，0 失败，最慢的一条 476 ms，全部在 1 秒内返回。

## 五、登录接口

登录是唯一包含密码哈希（BCrypt）的接口，成本固定在 CPU 上，不能与普通查询类比。

| 场景 | 结果 |
|---|---|
| 串行 10 次 | 中位 89 ms，P95 113 ms |
| 10 并发 8 秒 | 25–31 req/s，0 失败，P95 580 ms |

吞吐只有 25–31 req/s 是**有意设计**：密码哈希必须足够慢，否则离线爆破成本极低。系统另有「同账号连续 5 次失败锁定 10 分钟」的限流，正常登录场景（几十人分散登录）远达不到这个量级。

## 六、压测中发现并修复的性能缺陷

### 6.1 现象

第一版把「技能差距热力图」混入混合读场景后，整体吞吐从 1500 req/s 塌到 48 req/s，P95 从 19 ms 涨到 5.6 s。单独测该接口：单请求 287 ms，10 并发时 P95 达 1024 ms。

### 6.2 根因

`SkillGapService.skillHeatmap()` 复用了 `batchAnalyze()`，而后者是**逐个员工调用 `analyze(userId)`**，每个员工执行 5 条查询（用户、岗位、岗位技能要求、技能字典、员工技能）。64 个员工 = 每次请求约 320 条 SQL。

实测佐证（`SHOW GLOBAL STATUS LIKE 'Questions'` 前后差值）：

| 接口 | 每次调用产生的查询数 |
|---|---:|
| 技能热力图（优化前） | **388 次** |
| 课程分页（对照） | 3.6 次 |

这是典型的 N+1 查询。而且它会把 10 个数据库连接长时间占满，导致同一时刻其他读接口全部排队——所以混合场景的吞吐不是「变慢」，而是「被拖垮」。

### 6.3 修复

改为批量取数，固定 4 条查询：用户列表 → 这些岗位的技能要求 → 技能字典 → 这些员工在这些技能上的等级，之后在内存中聚合。

保留原有口径：跳过未配置技能模型的岗位、`gap = max(0, target - current)`、按加权差距降序。同时把并列分的排序改为 `avgGap 降序 → skillId 升序`，让结果可复现（原来是并列时按遍历顺序，不稳定）。

### 6.4 修复前后对比

| 指标 | 优化前 | 优化后 | 提升 |
|---|---:|---:|---:|
| 每次调用 SQL 数 | 388 | **6** | 65× |
| 单请求中位延迟 | 287 ms | **6.4 ms** | 45× |
| 10 并发吞吐 | 15.3 req/s | **793 req/s** | 52× |
| 10 并发 P95 | 1024 ms | **12.4 ms** | 83× |

**正确性验证**：修复前后分别抓取接口 JSON 输出，按 `skillId` 逐字段比对——全量查询（20 行）与按部门查询（10 行）**字段差异均为 0 条**，键集合完全一致。差异只出现在并列分的排列顺序上，而新顺序是确定性的。

## 七、顺带修正的接口规范问题

压测期间用 `GET` 探测登录接口，日志里出现一条「系统异常」。查明原因是全局异常处理器把所有未识别异常都按 500 处理：

- `GET /api/auth/login`（只支持 POST）→ 返回 `code=500 系统繁忙`，且记 `error` 级日志
- 访问不存在的路径 → 同样落到 500

已补两个分支：请求方法不支持返回 `code=405`，路径不存在返回 `code=404`，日志级别降为 `warn`。HTTP 状态码仍统一为 200（前端拦截器按响应体 `code` 判断，不改动既有约定）。

> 这一点对运维有实际意义：否则监控里会把调用方的错误全部计成服务端 5xx，误判系统健康度。

## 八、结论

1. **「接口响应 ≤ 2 秒」判定达标**。最慢业务接口串行 P95 为 10.8 ms，并发 30 下整体 P95 为 68.7 ms，均远低于阈值。
2. **小规模内网使用无压力**。200 个请求同一瞬间到达，0 失败，最慢 476 ms。
3. **吞吐上限受连接池约束**。Hikari 上限 10，30 并发即出现排队；若将来接入更多用户，优先调连接池与加缓存，而非改业务代码。
4. **已消除一处数量级缺陷**。热力图从 388 次查询降到 6 次，是本次压测最大的实际收益——它不仅慢，还会拖垮同实例上的其他接口。

### 论文可写的表述

> 在单机环境下（12 核 / 16 GB / MySQL 8.0 同机部署），对 7 个主要业务接口进行压测：串行请求 P95 延迟不超过 10.8 ms；10 并发下吞吐 1309 req/s、P95 19.2 ms；30 并发下吞吐 1464 req/s、P95 68.7 ms，全程无失败请求。200 个并发瞬时请求同一接口，全部在 1 秒内返回。针对技能差距热力图存在的 N+1 查询（每次请求 388 条 SQL），通过批量化改造降至 6 条，单请求延迟由 287 ms 降至 6.4 ms，10 并发吞吐提升 52 倍，输出结果经逐字段比对完全一致。

### 不能写的内容

- 不要写「支持 X 万用户」「高并发架构」——这是单机、单实例、无缓存的实测，规模上限受连接池与单库约束。
- 不要把登录接口的 30 req/s 当成缺点，要说明这是 BCrypt 与失败锁定的安全代价。
- 不要把 1309 req/s 写成「系统容量」：那是混合读接口在 10 并发下的瞬时吞吐，真实用户场景是几十人级别。

## 九、复现方式

```bash
# 1. 启动数据库（3307，避免与本机 MySQL80 抢 3306）
"D:/develop/MySQL/MySQL Server 8.0/bin/mysqld.exe" \
  --defaults-file="D:/develop/mysql-data/conf/ai-training.cnf" --port=3307 \
  --log-error="D:/develop/mysql-data/tmp-3307.err"

# 2. 启动后端（必须在 server 目录下执行，否则读不到 application-local.yml）
cd work/app/server
java -jar target/ai-training-server-1.0.0.jar --server.port=8000 \
  --spring.datasource.url='jdbc:mysql://127.0.0.1:3307/ai_training?...'

# 3. 跑压测
python outputs/loadtest_stable.py     # 串行基线 + 并发梯度
python outputs/loadtest_burst.py      # 瞬时突发 + 登录
python outputs/loadtest_heatmap.py    # 热力图专项
```

脚本与原始数据：

| 文件 | 内容 |
|---|---|
| `outputs/loadtest-stable.json` | 串行 8 接口 + 并发 10/30 三轮明细 |
| `outputs/loadtest-burst.json` | 突发 50/100/200 三轮中位数、登录串行 |
| `outputs/loadtest-heatmap.json` | 热力图并发 1/5/10 |
| `outputs/heatmap-before.json`、`heatmap-after2-all.json` | 优化前后输出比对样本 |
| `outputs/loadtest-v3-before.json` | 优化前对照（含塌陷现象） |

## 十、说明

1. 本报告所有数字均为实测，未做理想化修饰。采样环境有 14 GB 内存被其他程序占用，属于「不理想的机器」，但这恰好接近真实演示条件。
2. 客户端与被测服务在同一台机器上，会互相争抢 CPU，因此测得的吞吐偏保守。
