## 六、本次发现并修复的缺陷（2 个）

### 缺陷 1：5 个计划详情页必然报 500（严重）

**现象**：`GET /train/plan/{id}`，7 个计划里有 5 个返回 `{"code":500,"msg":"系统繁忙：null"}`，前端计划详情页白屏。

**根因**：`TrainPlanService.detail()` 第 216 行
```java
Map<Long, String> skillNames = skillIds.isEmpty() ? Map.of() : ...;
...
m.put("coverSkillName", skillNames.get(pc.getCoverSkillId()));  // NPE
```
手工编排的计划 `plan_course.cover_skill_id` 全为 NULL（数据库里实测 15 条空值）。`skillIds.isEmpty()` 成立 → 返回 `Map.of()`，而 **`Map.of()` 不接受 null 键查询**，`get(null)` 直接抛 NPE。

**修复**：把查表用的 `Map.of()` 改为 `Collections.emptyMap()`（`get(null)` 返回 null 而非抛异常）。共改 9 处，覆盖 `TrainPlanService`、`UserService`、`TrainProgressService`、`ExamService`。

**验证**：修复后 7 个计划详情全部正常返回，覆盖技能为空的课程显示 null 不再崩。

**同类隐患已一并处理**：`UserService` 的部门/岗位映射——一旦新建用户不填部门，用户列表就会整页崩，现在不会了。

### 缺陷 2：压测脚本断言文案与实现不一致（轻微）

断言逻辑本身正确（`Assertion.test_type=16` Contains、期望 `"code":0`、校验响应体），但断言名称和失败提示还写着「未返回 200」。已改为「未返回业务成功码 0」，避免答辩时被人追问「你到底断言了什么」。

## 八、论文口径必须改的三处

1. **不要说「向量检索」**——实现是 BM25。45 个知识片段、千级以内，词法检索足够，且得分可回溯。这是合理的技术选择，不是缺陷，但表述必须改。
2. **不要说「大模型自主决策选课」**——实测 HYBRID 与 RULE 的课程集合 Jaccard 0.948（16/20 完全一致），模型的增量在**说明文字质量**（摘要 95→134 字、引用 0→5 条），不在选课。定位成「可解释生成」站得住，定位成「自主决策」撑不住。
3. **约束的价值别说成「防幻觉」**——LLM_ONLY 幻觉只有 3 门，但 65% 的样本超预算（本次实测超支 55%）。正确表述：**约束保证方案可执行（预算内、课程数可控），不是防止编造**。

## 九、轻微问题（不影响验收）

| 问题 | 说明 |
|---|---|
| 错误返回 HTTP 200 + 业务码 | 越权时返回 `{"code":403}` 但 HTTP 状态是 200。前端拦截器能正确处理，功能安全；严格 REST 规范应返回 403。答辩被问就答「统一响应体 + 业务码，前端统一拦截」 |
