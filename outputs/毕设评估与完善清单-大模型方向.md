> 评估对象：AI 培训计划管理系统（2026-10-23 核查）
> 新题目：**基于大语言模型的 AI 培训计划管理系统设计与实现**

---

## 一、题目适配度：能撑住，但现在拿不出证据

### 结论

代码底子配得上这个题目，**但"基于大语言模型"这几个字目前只有代码，没有数据**。答辩时老师如果问"你怎么证明大模型起了作用"，现在答不上来。

### 现有实现的真实分量

| 维度 | 实际水平 | 依据 |
|---|---|---|
| AI 模块规模 | 2489 行，六个业务模块中最大 | 超过 train（1370）、exam（967） |
| LLM 应用场景 | 6 个 | 方案生成、主观题评分、知识库问答、效果诊断、补训建议、自动组卷 |
| 检索增强 | 自研 BM25（中文 2-gram + 英文词切分） | 内存倒排索引、IDF 打分、Top-K 阈值过滤、引用溯源 |
| 输出可靠性 | 三道防线 | JSON 清洗 → Schema 校验 → 规则兜底 |
| 可观测性 | 完整 | `ai_gen_record` 记录 prompt / 输出 / tokens / 耗时 / 重试次数 / 状态 |
| 前端呈现 | 到位 | 在线状态、混合/降级标识、耗时、降级原因、RAG 引用来源 |

**这套设计的核心不是"调 API"，而是"受约束的生成"**：规则引擎决定选哪些课（确定性、可解释），大模型只在候选集合内生成说明与排序理由。这是工程上更可靠的做法，也是你论文真正该写的创新点。

> 这个定位必须写进摘要和架构章节。否则会被人当成"套壳 Demo"。

### 三个缺口（决定题目立不立得住）

1. **没有实测记录** —— `ai_gen_record` 里如果没有真实调用数据，等于没有证据
2. **没有对比实验** —— 论文最需要的那张表（规则 vs 混合）还是空的
3. **LLM 作用面偏窄** —— 只影响"说明与顺序"，课程集合完全由规则决定

## 二、必须补的（P0，不补题目站不住）

### P0-1 配好 API Key，跑通全链路并留下记录

- 申请 DeepSeek Key，配到 `application-local.yml` 或环境变量 `DEEPSEEK_API_KEY`
- 用 5～10 个有技能差距的员工各生成一次方案，确认 `ai_gen_record.status = SUCCESS`
- 同时验证降级路径：临时填错 Key，确认能自动降级且 `status = API_ERROR`

**验收标准**：`ai_gen_record` 里 SUCCESS / FALLBACK / API_ERROR 三种状态都有真实数据。

### P0-2 设计并跑一组对比实验

这是论文的数据来源，也是答辩最硬的证据。

| 项目 | 设计 |
|---|---|
| 样本 | 20～30 份员工档案（覆盖不同岗位、不同差距数量） |
| 对照组 | 纯规则（`allowLlm=false`） |
| 实验组 | 混合模式（规则 + LLM） |
| 重复次数 | 每组每样本跑 3 次（观察稳定性） |
| 记录指标 | Schema 校验通过率、降级率、平均响应耗时、平均 token 消耗、课程集合与规则方案的重合度、RAG 引用命中数 |

**产出**：一张对比表 + 一张失败案例分析（模型输出不合规的典型例子 + 校验器如何拦截）。

> 数据已经自动落在 `ai_gen_record` 里，写个统计 SQL 就能出表，不用额外埋点。

### P0-3 论文里把"混合架构"讲成方法论

建议的表述结构：

1. 纯 LLM 生成的问题：幻觉课程、学时失控、结果不可复现
2. 本系统的做法：规则做候选集约束，模型做语义生成
3. 可靠性保障：JSON 强制模式 → 结构校验 → 降级兜底 → 全链路记录
4. 效果：通过率 / 降级率 / 耗时 / 成本四个指标

## 三、技术债（P1，可能被追问）

### P1-1 LLM 调用没有超时（真实缺陷）

`application.yml` 里配了 `ai.llm.timeout-seconds: 90`，但代码里**从未使用**：

```java
// LlmClient.java:39  当前写法，无任何超时
client = RestClient.builder()
        .baseUrl(props.getLlm().getBaseUrl())
        .build();
```

后果：模型接口卡住时，请求线程会一直等下去，直到 Tomcat 线程耗尽。

**修法**：给 RestClient 配 `JdkClientHttpRequestFactory`，设 connectTimeout 与 readTimeout，取 `props.getLlm().getTimeoutSeconds()`。

> 顺带修：`client` 字段懒加载没有加锁，首次并发调用可能创建多个实例，加个 `synchronized` 或改成构造后初始化。

### P1-2 没有任何单元测试

`src/test` 目录不存在。三个最该测的、且不依赖数据库的类：

- `PlanSchemaValidator` —— 各种畸形 JSON 的拦截
- `RulePlanEngine` —— 预算约束下的选课与学时分配
- `RagService.tokenize` / BM25 打分 —— 中文切分与排序正确性

写 15～20 个用例即可，成本低、收益高（答辩时可提"关键算法有测试覆盖"）。

### P1-3 方案页没展示 token 消耗

数据在 `ai_gen_record` 里已有，`plan.vue` 只展示了耗时。补一行 token 统计，成本对比才完整。

## 五、答辩预判：三个必被问的问题

**Q1：大模型在这里是不是只负责写文案？**

应答要点：不是写文案，是**受约束的语义生成**。模型在候选课程集合内决定顺序与理由，同时独立承担主观题评分、知识库问答、效果诊断、补训建议四个场景。课程集合由规则确定，是为了保证可复现与学时可控，这是设计选择而不是能力缺失。

**Q2：为什么不用向量数据库？**

应答要点：知识片段在千级规模，BM25 零外部依赖、离线可用、检索过程可回溯（每个命中片段都有得分）。引入 Embedding 服务与向量库会显著增加部署复杂度，收益在当前规模下有限。架构上已预留混合排序的扩展位。

**Q3：模型输出不可靠怎么办？**

应答要点：四层保障。强制 `response_format=json_object` → JSON 清洗容错（去 Markdown 包裹）→ Schema 校验（课程必须在候选集内、学时合计不超预算）→ 失败即降级为规则方案。所有调用写入记录表，可按 `status` 统计失败率。
